F) Request counter

Plan:  class RequestCounter { increment():number // before each fetch (incl. fallbacks), value, budgetString(): "N/1000" }
Oxalpha: class Budget { load(), record(), snapshot(): {runRequests,today,minute} } // persisted to work/state.json, record() after success only
  • Timing bug: increments after chat() success L41, not before fetch → 429/timeout attempts undercounted (e.g., 429+success reports 1 not 2).
  • Visibility: every ProgressEvent should carry requestCount — oxalpha splits into request:start (no count) / request:end (runRequests/today/minute). No per-event requestCount.
  • Extra: daily/minute sliding window + work/state.json persistence exceeds plan's per-run counter (plan deferred cross-run tracking).
  • No assert counter ≤3.

Bottom line vs muse plan

Oxalpha keeps the one-fetch + shell-out + strict TS skeleton but rewrites the contracts (Budget vs Counter, type vs phase/status, validate→clamp vs validate→reject) and request shape (response_format, temps) so it is not drop-in compliant with grep + validate + counter≤3 + clip fallback integration checks. Highest priority fix is validate.ts strict mode — everything downstream (clips, SSE, counter) depends on trustworthy timestamps.
